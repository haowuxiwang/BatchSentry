# 上传限额（体积 / 页数）——市面做法调研与定标依据

> 状态：v1.1.2 已实现（单一真值 `config.UPLOAD_LIMITS`）。
> 起因：2026-09-15 用户提问"面对不同尺寸、方向、大小的 PDF 是否都能应对？
> 超出能力边界也能给出良好提示？"——排查发现**页数完全没有上限**，同时
> 同一个 200MB 被四处各自写死。本文记录调研结论、定标推导与设计。

## 1. 问题

体积上限（200MB）**挡不住"低密度但极长"的 PDF**：数字排版件可能 50KB/页，
200MB 能装下数千页，而体积检查毫无察觉。数千页按实测 9.0 s/页 OCR 会先撞上
`core/ocr_client.POLL_TIMEOUT_MAX = 3600s`（100 页即封顶）→ 用户等满 1 小时
后才收到"轮询超时"。**能在上传时说清楚的事，不该让用户在服务端超时后才知道。**

## 2. 市面成熟做法（2026-07 核实）

| 产品 | 单文件体积 | 单请求页数 | 超限行为 |
|---|---|---|---|
| Azure AI Document Intelligence (S0) | 500 MB | 2,000 | 硬性、**不可上调** → 自行拆分 |
| Azure (F0 免费档) | 4 MB | 前 2 页 | **只回前 2 页、不报错也不解释** |
| AWS Textract（异步 / 同步） | 500 MB / 10 MB | 3,000 / 1 页 | 拆分 |
| Google Document AI（在线 / 批量） | 40 MB / 1 GB | 15（30 无图）/ 1,000 | 超 15 页必须走批量作业 |
| Mistral Document AI | 50 MB | 1,000 | — |
| Claude（对话） | 500 MB | 1,000（>100 页退化为纯文本） | 报 `Uploaded file is too large` |
| Veryfi | — | **默认 15 页** | 截断到 15 页；文档明确这是"防失控任务的**安全默认值**，不是能力上限"，`max_pages_to_process` 可调 |
| amaise | — | 2,000 | **拒绝 + 说明 + 下一步**：`Too many pages (max 2,000) — split the PDF.` |
| Autodesk BIM 360 | — | 500（Plans）/ 2,000（项目文件） | 按文件夹类型设不同上限 |
| Unique AI | 512 MB | — | **上传开始前**即以 toast 报错并给出当前上限 |

> **单页经济性对照**（2026-08 公开牌价，多源交叉核对，出处见本节末）：三大云
> 纯文本抽取（Azure S0 `Read` / AWS Textract `DetectDocumentText` / Google
> 纯文本）统一约 **$1.50 / 1,000 页**，超百万页降至 $0.60；结构化与生成式抽取
> **$10~50 / 1,000 页** —— 相隔 **10~30 倍**。上表的页数上限（1,000~3,000）
> 正是落在**前者**的成本档上才敢取。

### 提炼出的原则

1. **体积与页数是两个正交限额**，都要在入口强制。只设体积会漏掉"低密度
   极长"文件；只设页数会漏掉"单页巨图"。
2. **拒绝必须可执行**：含真实值 + 上限值 + 下一步动作。amaise 的
   `— split the PDF` 是最佳范例。
3. **绝不静默截断**。Azure F0 只回前 2 页且不解释，被业界反复引为反面教材。
4. **限额的定位是"防失控任务的安全护栏"，不是能力宣言** —— Veryfi 原文如此
   表述，故其默认值敢于取到 15。
5. **报错时机越早越好**：Unique AI 在上传开始前就拦，避免用户白等一次上传。
6. ⚠️ **页数数字不能跨产品照抄** —— 上限是"单页能承受的代价"的函数。三大云
   纯文本抽取统一约 **$1.50 / 1,000 页**（=$0.0015/页），才敢对单请求写
   1,000~3,000 页；而结构化与生成式抽取是 **$10~50 / 1,000 页**，相差
   **10~30 倍**。本链路每页跑手写体 OCR + 一次逐页 LLM 生成，按调用性质属
   最贵档，且实测 **9.0 s/页（OCR）+ 22.8 s/页（LLM）**。**可移植的量是
   "墙钟时间预算"，不是页数。**

**本节出处**（2026-09-15 核对；价格会变，采购前请复核）：
- **Azure S0 `Read`** = $1.50 / 1,000 页（effective 2022-03-01；超百万页 $0.60）。
  定价页对未鉴权抓取会渲染为占位符，故**以 Microsoft 零售价 API 为准**；
  §2 表中的 2,000 页硬上限来自 S0 服务限制。
- **AWS Textract `DetectDocumentText`** = $1.50 / 1,000 页（超百万页 $0.60）；
  同表 `Tables` $15 / `Forms` $50 / `Analyze Lending` $70，交叉核对 AWS
  Price List API。
- **Google Document AI** 纯文本抽取约 $1.50 / 1,000 页；结构化档约 $10 / 1,000 页。
- 上述"纯文本档 vs 结构化/生成式档相差 10~30 倍"的比值，及 Google 档位，
  取自第三方横向比价
  <https://www.ud.com.hk/zh-Hant/blogs/insight/article/ai-document-processing-costs-2026-08-11>；
  该文亦声明其数字为各厂商公开牌价。
- ⚠️ **本项目自身不含任何"每页耗时"的第三方数字** —— 单页耗时一律用自测值
  （见 §3），因为各家公布的是**价格**而非**延迟**，两者不可互换。

## 3. 本项目的定标推导

### 实测基线（job `95a27d88-52b`，真实 51 页手写批记录，Paddle 后端）

| 阶段 | 实测耗时 | 单页 |
|---|---|---|
| Stage 1 OCR | 460,535 ms | **9.0 s/页** |
| Stage 2 逐页 LLM 分析 | 1,163,738 ms | **22.8 s/页** |
| 全链（含跨页语义分析） | 1,889,115 ms | 32.7 s/页 |

### 既有耦合约束

`core/ocr_client.poll_timeout_for()`：`min(600 + 30×页数, 3600)`。
**100 页起轮询上限就封顶在 1 小时**，之后不再增长。按 9.0 s/页，400 页即
打满；而代码自身记载"拥堵日单页排队 500-1000s"（见 `static/eta.js`），
故不能贴边取值。

### 取值

| 限额 | 值 | 依据 |
|---|---|---|
| `max_pages`（硬） | **200** | OCR 预估 1800s = 3600s 上限的一半 → **2× 余量**抗拥堵；全链预估 ≈1.8 h；高于单批记录合理规模（典型 20~120 页，本样本 51 页）1.6~10× |
| `warn_pages`（软） | **80** | 全链预估 ≈44 分钟，已超出"用户会一直盯着屏幕"的范围 → 值得**事先告知**而非沉默接受 |
| `max_bytes` | 200 MB（不变） | 与 MinerU 通道厂商上限对齐，见 §4.3 |

### ⚠️ 诚实披露

200 页上限是**基于 51 页实测的线性外推**，**未以 200 页文件实跑验证**。
外推风险：分片 / 并发 / 上游队列行为可能非线性。真正的验证需要一份 ≥200 页
的真实文档 —— 建议并入 R4（人工标注集）一并做，见
`docs/ARCHITECTURE_AND_QUALITY_REVIEW.md` §5。

## 4. 设计

### 4.1 单一真值

`config.UPLOAD_LIMITS` 是唯一来源，**三处派生**：

```
config.UPLOAD_LIMITS
  ├─ 后端强制   api/jobs/__init__._MAX_PDF_BYTES + config.check_upload_page_limits()
  ├─ 前端预检   window.__PBC__.limits → static/upload.js
  └─ 页面文案   templates/upload.html
```

历史缺陷：200MB 曾被**四处各自写死**（后端常量 / 后端错误消息 /
`static/upload.js` 比较式 / `templates/upload.html` 提示文字）。改为派生后，
漂移会被 `tests/unit/test_upload_limits.py` 的源码扫描护栏当场拦下。

**前端刻意不设兜底数值**：兜底副本会随服务端调整而漂移，"前端放行、后端
拒绝"正是要根除的缺陷。注入缺失时跳过前端预检，交由服务端判定（服务端本
来就权威，其 `detail` 会被 HTTP 错误分支展示），只是多一次往返。

### 4.2 两层策略（拒绝 / 告知）

判定抽成纯函数 `config.check_upload_page_limits(page_count, limits)`：

| 情形 | 行为 |
|---|---|
| `page_count <= 0`（读取失败） | **放行**。部分损坏 PDF 云端 OCR 各有容错，拦掉等于把"可能成功"变成"必然失败" |
| `> max_pages` | **拒绝**（400），消息含真实页数 + 上限 + "请按批次拆分" |
| `> warn_pages` | 放行，响应带 `page_warning`（预估耗时），并写 `audit_log` 留痕 |
| 其余 | 放行，不发声 —— 对常态文件刷告警等于没有告警 |

前端收到 `page_warning` 时会**延长跳转延迟至 5s**：1.5s 读不完一句耗时
提示，等于没有告知。

### 4.3 与厂商上限的关系（failover 安全）

`core/mineru_client.MINERU_MAX_UPLOAD_BYTES` 是 **MinerU 通道的厂商上限**，
不是本产品的策略。二者当前数值相同纯属巧合，语义不同。

MinerU 是 Paddle 提交失败时的 **failover 备选**：一份被我们放行、却被 MinerU
拒收的文件会在流程中途失败，而用户已经等过一轮 OCR。故
`test_policy_limit_does_not_exceed_mineru_vendor_limit` 机检
`UPLOAD_LIMITS["max_bytes"] <= MINERU_MAX_UPLOAD_BYTES`，防止将来只改一边。

（Paddle 侧代码中无体积/页数限制，只有随体积增长的动态上传超时。）

## 5. 如何调整

环境变量覆盖（非法值由 `_normalize_upload_limits` 收敛，不崩溃）：

```powershell
$env:MAX_UPLOAD_BYTES = "524288000"   # 500 MB
$env:MAX_UPLOAD_PAGES = "400"
$env:WARN_UPLOAD_PAGES = "120"
```

收敛规则：`max_pages < 2` → 回默认 200（1 页上限等于拒绝一切多页批记录，必是
误配置）；`warn_pages` 不在 `[1, max_pages)` 内 → 收敛为 `min(80, max_pages-1)`。

调整后必须同步 `tests/unit/test_upload_limits.py::test_shipped_defaults_are_the_documented_ones`
与本文的取值表 —— 该测试就是为此而存在。

## 6. 未决 / 后续

- **200 页上限未经实跑验证**（见 §3 诚实披露）。
- **未定**：是否支持"拆分为多段、服务端自动拼接"。成熟产品多把拆分推给用户
  （Azure 明确不可上调、需自行拆分），但 Google 走"批量作业"路线。本项目
  目前与 Azure 同路线（用户自行拆分）。
- **未定**：MinerU/Paddle 的**上游页数**上限未核（体积上限已核为 200MB）。
  若上游存在页数限制，应并入 §4.3 的关系护栏。

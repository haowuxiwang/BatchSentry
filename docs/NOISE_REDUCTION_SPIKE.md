## 0. 两个问题的直接答案

| 问题 | 答案 |
|---|---|
| paddle / mineru 能否按**单元格**对齐？ | **不能。** 两个后端都**不提供单元格级坐标**，只有块/区域级 bbox。可行对齐粒度是**表级**（bbox 匹配）与**字段级**（标签文本匹配），页级为兜底。 |
| PaddleOCR-VL 是否回传单元格 bbox？ | **回传 bbox，但是区域级、不是单元格级。** 另有区域级版面检测 `score`，**不是**文字识别置信度。 |

## 1. PaddleOCR-VL 真实返回结构（区域级 bbox 确认存在）

`result.layoutParsingResults[i]` 的 `prunedResult` 子键：

```
page_count, width, height, model_settings, parsing_res_list,
doc_preprocessor_res, layout_det_res
```

**块级坐标**（`parsing_res_list[]`，本次 378 块）：

| 键 | 含义 |
|---|---|
| `block_label` | 区域类型（table / text / seal / doc_title / vision_footnote / number …） |
| `block_content` | 文本或**表格 HTML**（含 `rowspan` / `colspan`） |
| `block_bbox` | `[x0, y0, x1, y1]` — **块级**包围盒 |
| `block_polygon_points` | 四点多边形（版式倾斜时比 bbox 更准） |
| `block_id` / `block_order` / `group_id` | 顺序与分组 |

**版面检测**（`layout_det_res.boxes[]`，本次 469 个区域）：

| 键 | 含义 |
|---|---|
| `label` / `cls_id` | 区域类型 |
| `coordinate` / `polygon_points` | 区域坐标 |
| **`score`** | **版面检测置信度**（非文字识别置信度） |

`score` 实测分布（n=469）：`min 0.300 / p10 0.339 / p50 0.545 / p90 0.893 / max 0.977 /
mean 0.579`；`<0.6` 有 267 个、`<0.5` 有 198 个。

> ⚠️ **不可把它当"抽取可信度"用**：低分区域绝大多数是 `text` / `inline_formula` /
> `figure_title` 这类小文本块 —— 版面检测器对小文本天然低分，而它们的**文字识别**
> 完全可能是对的；反过来 `table` 区域 0.82 也不代表表内数字读对了。
> 这印证了 `core/hw_signal.py` 已登记的判断：**PaddleOCR-VL 不提供文字识别置信度**。
> 它作为**区域定位**证据可用，作为**数值正确性**信号不可用。

**是否持久化**：`page_cache` 只有 `job_id / page / raw_html / structured_json /
analyzed_at / ocr_diagnostics` —— **坐标与 score 100% 被丢弃**（`markdown.text` 是唯一下游输入）。

|---|---|---|
| `*_content_list_v2.json` | 9.4 KB | ✅ 块级 `bbox` |

- `layout.json` 层级：`pdf_info[] → preproc_blocks[]/para_blocks[] → blocks[]

  ```
  {"type":"table","bbox":[46,76,594,138],
   "blocks":[{"type":"table_body","lines":[{"spans":[
      {"type":"table","html":"<table>…</table>"}]}]}]}
  ```

- `_model.json` 关键词计数：`cell` **0** 次、`rowspan` **0** 次、`colspan` **0** 次
  （`bbox` 35 次、`score` 17 次）。→ **单元格级结构在 MinerU 侧根本不存在。**

### 2.1 一处需要澄清的误判风险（已排除）

样本里 MinerU 的表格 HTML 出现了 `工序编号 | 工序名称 | …` 这种**伪单元格**（`<td>|</td>`）。
直接抽 `origin.pdf` 的原始 text 验证：**源 PDF 第 2 页本身就写着 13 个 `|` 字符**
（`工序编号 | 工序名称 | 开始时间 | …`）。所以这是**合成样本自身用竖线造表的产物，
不是 MinerU 缺陷**。真实批记录用画线表格，不会出现。

> 保留的结论：MinerU 的 HTML 栅格**不保证语义正确**，但成因是"源文有竖线"而非模型错误。
> 我们的真实 51 页记录中未观察到该现象。

## 3. 为什么"单元格对齐"做不到，以及可行的三级替代

**根因**：两个后端都把表格当成**一个区域**来检测和输出（Paddle 一个 `table` 块、
MinerU 一个 `span`），表格内部的单元格只存在于 HTML 字符串里，**没有任何一方给出
单元格的行列索引或坐标**。

可行的三种对齐粒度（供 P0-1 选）：

| 粒度 | 依据 | 成本 | 能力边界 |
|---|---|---|---|
| **页级**（现状） | 页码 | 0 | `dual_compare` 现在就是这个。只能得出"这页有差异"，无法定位到字段 |
| **表级** | 表级 bbox 归一化（用 `prunedResult.width/height`）后做 IoU / 中心点匹配 | 低（双方都有数据） | 能对齐"同一张表"。风险：跨后端表切分可能不一致（一方并表/拆表） |
| **字段级** | 标签文本归一化（去空白 / 下划线 / 括号 / 全角）后在同页内匹配 | 低 | **最贴近我们的缺陷类别**。p08 温度、p09 使用次数、p19 纯度都有稳定标签 |

**建议组合**：**表级做粗筛（限定候选范围）+ 字段级做判定**，页级作兜底。
不需要单元格坐标 —— 我们真正要比的是"同名字段的两个读数"，不是像素级单元格对应。

## 4. Spike 顺带定位到的 4 类新缺陷（含已修 1 类）

### D1 ✅ 已修：`_parse_spec` 书写变体缺口（7 种形态）

真实落库 `spec_range` 中，**语义完全等价但此前解析失败**的写法：

| 形态 | 真实样例 | 落库出现 |
|---|---|---|
| LaTeX `\pm`（Paddle 把印版 ± 读成 `\pm`） | `温度(15 \pm 5°C)` | 51 页原始输出 **16 处 / 12 页** |
| 同上且外层裹 `$` | `15 $ \pm $5°C` | 同上 |
| 全角波浪线 `～`(U+FF5E) | `99%～101%` | 1 处（同语义半角 `99%~101%` 15 处成功） |
| U+2212 减号 / 全角连字符 / em dash | `15−25` / `15－25` / `15—25` | — |
| **单位夹在数字与分隔符之间** | `972 μg/mg ~1020 μg/mg` | **20 处（全部解析失败）** |
| 外层括号 | `(1300~3200)` | 1 处 |

**最高影响是"单位夹分隔符"**：20 处全是 `含量`/`效价`（关键质量属性）规格，
原本静默降级为 `spec_unverifiable` 送人工。

**修复**：`core/rules/parsing.py` 新增 `_normalize_spec_notation`（只归一书写形状，
不改判定语义）：剥外层括号 → 全角/Unicode 符号归一 → LaTeX `\pm|\mp|+/-|+-` 归一为 `±`
→ 同单位夹分隔符折叠（**保留串尾单位**，因为 `_try_unit_normalize` 依赖它做实测值换算）。
调用点在 `≤/≥ → <=/>=` 归一**之前**（± 分支靠字形区分 `±` 与 `≤`）。

**真实数据验证**（3526 个 `(spec, value)` 对，用 `git show HEAD:` 取修复前版本做对照）：

```
修复前无法解析 → 修复后可解析: 22 处
解析结果变化（回归风险）    : 0 处
新增可判定中判为超差        : 0 处     ← 纯降噪，不引入新误报
```

**仍不可解析的 31 种形态**全部是**正确的 fail-closed**：`是/否`(367)、`符合规定`(61)、
`蓝紫色结晶性粉末`(21)、`14`/`1.4`/`1.5`/`90`/`14 L/min`（裸数字/裸量，无法确定区间语义）。

**测试**：`tests/unit/test_cross_page_analyzer.py` 新增 9 项（`test_parse_latex_pm_spec`、
`test_parse_fullwidth_tilde_range`、`test_parse_unit_straddling_separator`、
`test_normalization_keeps_fail_closed` …），223 passed。

### D2 ⛔ 未修：Paddle 多行单元格的**分隔符不确定** → 值融合（p9「417」真根因）

**修正 M8 的表述**。此前记为"OCR 把两个相邻单元格粘进同一 `<td>`"。真实结构是：

Paddle 把**整个多行区块压成 1 个 `<tr>` + 两个多行 `<td colspan=N>`** —— 左格是
"标签列"、右格是"值列"，**标签↔值只靠行序对应**：

```html
<td>T2101a 是否符合要求\n…\nSP-207 树脂批号\n本批树脂使用次数\n预处理液停留时间</td>
<td colspan="3">✓ 是 / ◊ 否\n…\nA000626-221201/4\n17 次\n✓ 是 / ◊ 否</td>
```

**同一份 51 页文档里，分隔符形态不一致**（这是关键）：

| 页 | 字面 `\n` | 真换行 | 结果 |
|---|---|---|---|
| p09 | 23 | 21 | 值列有分隔 → `A000626-221201/4` / `17 次` 正确成两行 |
| p21 | 1 | 21 | **无分隔符** → `…否☑是/☐否A000626-2212017 ☐次☑是/☐否` 全串连 |

一旦分隔符丢失，**上一行的值与下一行的值直接融合**：`A000626-221201/4` + `17 次`
→ `A000626-221201/417 次` → 规则层与 LLM 层**同时**读到 `417`（规格 ≤100 → 双双报超差）。
这解释了为什么"规格 vs 实测"的交叉复核抓不到它：规格是对的、数字看起来也合理。

> 附带结论：`417` 在不同轮次表现不同（8/26 轮次该页显示 `A000626-2212017 ☐次`），
> 说明这是**服务端非确定性行为**，不是稳定可复现的单一模式 → 不能靠"看到 417 就修"。

**为什么不能靠启发式修**：无法从"融合后的字符串"可靠地还原切分点（`…221201` 之后
该切在第几位？）。可行方向见 todolist（T-P1-1 结构校验 / T-P1-2 行序配对校验）。

### D3 ⛔ 未修：LLM 输入的换行语义混乱 + LaTeX 残渣

- 同一份输出里**字面 `\n`（193 处）与真换行（1057 处）混用** —— 同一"多行单元格"
  在 HTML 文本里是 `\` `n` 两个字符，在别处是真换行。LLM 需要猜。
- `$…$` LaTeX 残渣 **144 处**（`$ m^{3} $`、`$ \pm $`、`13.6m^{3} $`），
  数字与单位被公式定界符割裂（`13:6  $ m^3 $` 连小数点都退化成冒号）。
- 影响：LLM 抽 `value` 时的切分与单位归一都受影响；`_parse_number` 已做 `$` 剥离，
  但规则层拿到的 `value` 已由 LLM 决定。

### D4 ⛔ 未修（设计护栏）：记录频次 `±` 不是规格，但共用 `±` 字形

`\pm` 在本次真实输出中**分两种角色**：

1. **真规格**（控制参数公差）：`回流温度 15±5°C`、`热水 70±5°C`、`浓缩液 40±3°C`、
   `缓冲液 pH 7.5±0.2`、`热水 40±5°C`
2. **记录频次噪声**（附表标题里的采样间隔）：**"每1小时±5分钟记录一次"** —— 出现在
   p10 / p11 / p17 / p18 / p20 / p21 / p22 / p26 等 **12 页**

两者字形完全相同。**任何"宽 ± 解析"的改动都必须只作用于 `spec_range`，绝不可
作用于正文文本**；当前的 `_parse_spec` 是"从字符串开头锚定 + 只允许非数字尾随"，
天然挡掉 `每1小时±5分钟…`（首字符是 `每`），该护栏需在后续改动中保持并加测试。

## 5. 对 P0 决策的影响（结论）

1. **P0-1 选择性双读仲裁**：不要按单元格对齐，改用**表级粗筛 + 字段级判定**。
   页级（现状）会把整页所有结论都标"待仲裁"，太粗。
2. **P0-3 证据锚**：可做到**区域级高亮**（表级 bbox + 页宽高归一 → 点击回页并框出该表），
   **做不到单元格级高亮**。区域级 bbox 是白拿的（数据已在响应里，只是被丢弃）。
3. **Paddle 上游不可用是常态**（本次 spike 期间实测两次 `code 10010 任务提交队列已满`，
   与第二轮 e2e 触发 `ocr_failover paddle→mineru` 同一状况）→ **P0-1 必须把
   "第二读取不到"定义为 `needs_arbitration`（fail-closed），不得静默采信第一读。**
4. **不要用 Paddle 的 `layout_det_res.score` 当抽取置信度**（它是版面检测分，
   均值 0.579、小文本块天然低分）。

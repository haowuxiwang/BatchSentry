## 1. 上传一个文件 → 回首页 → 再上传第二个文件：现在怎么处理？

**结论：能处理，但"能"指的是"不会崩、不会串"；用户会碰到两条硬规则（重复 409 / 并发上限 409），
且第二条的提示是"请等待完成或取消后再试"，没有队列。**

**实测**：

| 行为 | 证据 |
|---|---|
| 单文件上传成功后**自动跳转**复核页（1.5 s；有 `page_warning` 时 5 s） | `static/upload.js:531-535` |
| 多文件上传**不跳转**（跳走会杀掉其余上传），改由任务列表承载 | `static/upload.js:519-524` |
| 上传页**有**任务列表：`/api/jobs?page=&page_size=20` + 归档列表 + 活跃任务 SSE | `static/upload-jobs.js:184`、`:283`、`:854` |
| 内容 md5 相同 → **409**，前端给"仍要重新上传"（`force=1`） | `api/jobs/upload.py:482-496` |
| 活跃任务数 ≥ `MAX_CONCURRENT_JOBS`（默认 **5**）→ **409** | `api/jobs/__init__.py:117`、`api/jobs/upload.py:193-199`、`:468-477` |
| 配额检查做了**两次**（早检 + 临界区内晚检），防并发绕过 | `api/jobs/upload.py:192`、`:468` |

**缺口**：

1. **没有队列**。第 6 个任务直接被拒（409），不是"排队等"。文案是"请等待完成或取消后再试"，
   用户只能反复手点。对"一次交 10 批记录"的用法，这是硬墙。
2. **单文件自动跳转**意味着：用户想连着传第二份，得先按返回。跳转是 `window.location.href`（硬跳），
   上传页的 SSE 连接随之断开 —— 第二份只能从首页重新开始。
3. `MAX_CONCURRENT_JOBS` **只能靠环境变量改**（`MAX_CONCURRENT_JOBS`），设置页里没有。

## 13. OCR 出错、LLM 漏掉内容：我们现在怎么办？（**重点**）

**结论：现在做的是"**宁可多报、不许静默**" —— 错了要**看得见**、要**留痕**、要**能人工兜底**；
但"漏了多少"这个数**我们现在给不出来**，因为没有真实标注集。**

### 13.1 已经做的（每条都有代码位置）

| 失败形态 | 处理 | 证据 |
|---|---|---|
| OCR 某页没出字 | 自愈重试 → 仍空则进 `failed_pages`，job 以 **`partial_review`** 收尾（**不是静默 `review`**） | `core/pipeline/stage1.py:148`、`stage2.py:66` |
| OCR 把页读歪（90°/270°） | 旋转自愈，记录 `rotation_deg` 证据 | `core/pipeline/self_heal.py:384` |
| 双引擎结果不一致 | 差异做成 findings 并**强制** `partial_review` | `core/pipeline/dual_compare.py:16` |
| LLM 被 `max_tokens` 截断 | 采 `finish_reason`，截断型**跳过** fix-hint 重试（省一次白烧） | `_migrate_v13`、0-38 |
| LLM 返回不合 schema | 显式 `_schema_warn`（**非静默**），并重试一次 | 0-40 消费侧复核 |
| LLM 报了个定位不到原文的 finding | `spec_guard` **fail-closed 保留**（宁可多报交人工） | `core/rules/spec_guard.py:17`、`:143` |
| 人工判定"这页 OCR 就是不行" | 页级**豁免**，写 `page_cache.ocr_diagnostics.exemption` + `audit_log`（`ocr_exemption`） | `api/review.py:629-645` |
| 每次 LLM 调用 | 全量落 `llm_call_audit`（provider/model/token/latency/success） | `api/review.py:735-750` |

**一句话**：现在的策略是**"失败必须显式化"** —— 不完整页、双引擎分歧、截断、schema 违约，
都会变成**用户能看到的信号**（`partial_review` + 页内横幅 + findings），而不是"看起来成功其实少了几页"。

### 13.2 还差的（**这些是真实的漏洞，不是"待优化"**）

1. **漏检率不可测**。没有标注集 ⇒ 精度/召回**没有任何可信数字**。
   首个真实样本已登记（`real_samples`），但 `label:null` / `intent_confirmed:false`
   ⇒ 它只证明"样本在"，**不产生 P/R**。
2. ~~**0-42（P1，未修）**：`llm_checks` 的三处裸 dict 模板不编码 `time`/`step_no`
   ⇒ 同一单元格**多个时间点会被 UNIQUE 索引静默合并**（含 `param_out_of_spec`）。~~
   ⇒ **已于 2026-10-15 修复**（本轮）：新增 `_where_tag(q)`，把 `步骤N`/`时间`
   编进 `第{p}页` 之后，三个产出分支统一调用；两者都没有时返回**空串** ⇒
   旧文案**逐字节不变**（不制造"（步骤None）"）。原 2 条 xfail 转绿，
   另加 2 条兼容性用例；变异 **4/4**（关标签 / 只丢 time / 只丢 step_no /
   无字段仍拼垃圾标签），每条后 sha256 逐字节还原。
   ⚠️ **这不等于"漏检率可测了"** —— 它只堵住"同一格多时间点被合并"这一个静默通道。
3. **0-41（P2，未修）**：一页参数超过 50 个时，参数判定被"参数数量过多"**整体吞没**
   ⇒ 该页 0 条 `param_out_of_spec`（实测值 `6.88` 零命中）。
4. **没有"漏检发现机制"**：现在只能靠人工复核**碰巧**发现漏项。没有抽样复核、
   没有"高价值页二次判定"、没有"规则命中率异常"告警。

### 13.3 我的建议（按性价比排序）

1. **先修 0-42**（P1）：它是"静默丢数据"，和整个设计原则冲突，且改动面小。

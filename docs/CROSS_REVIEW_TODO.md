### CR-28 · 签名先后一律不构成异常 —— 已完成（判据比初稿窄）

**现象**：用户裁定「复核人时间早于检查人，这是正确的行为」（p7/p8 为正确行为）。

**实际改法**：`core/rules/llm_finding_guard.py` 新增

⇒ 抑制。位置在 `_check_same_day_contradiction` 之后、**来源过滤之前**（覆盖 `user_rule`）。

### CR-1 · 护栏理由不得进入用户可见文案

**现象**：`apply_review` 把降级理由以 ``{正文}｜{理由}`` **追加到 `description`**。
实测 p22 的 `1563` 是最恶性形态 —— 业务正文本身为空，追加后**整条只剩**
「｜LLM 独断 critical，未经规则层确定性判据复核 ⇒ 降为 warning 待人工核对」，
用户看到的就是一句后端日志。

**实际改法**（四层，缺一层就"看起来修好了"）：

| 层 | 改动 | 失效形态（若无） |
|---|---|---|
| 纯函数 | `apply_review` 把理由写进 `nf["guard_reason"]`，**不再动 `description`** | 文案继续被内部语污染 |
| schema | `db/schema.sql` 两表加 `guard_reason TEXT`；`SCHEMA_VERSION 14→15` + `_migrate_v15` | 老库缺列 ⇒ 写入报错 |
| 写路径 | stage2 / stage3 / 归档 INSERT 全部带该列 | 加了列没人写 = 静默失效 |
| 空正文 | `core/finding_quality.has_business_text`，两个写入口共用；空文案**不写行**并计数进日志 | `1563` 形态回归（空卡片） |

⚠️ **初稿第 ④ 项"前端折叠区渲染系统判定说明"本批不做**：本批目标是"别把内部语
当业务文案"，再加一块展示内部语的 UI 需要单独的设计判断（且前端在 R103 才动）。
`guard_reason` 已在 `/findings` 响应里返回，R103 可直接用。

**历史数据**：库里已有 56 条被污染的行（55 条可拆 + 1 条 `1563` 整条只剩理由）。
**不放进迁移**——"正文到哪里结束"是业务判断，迁移里猜分隔符等于静默改写业务记录
（`PROJECT_PITFALLS` 六十八① 同一条纪律）。改为脚本
`scripts/split_guard_reason.py`：默认 dry-run，`--apply` 才写且先备份；
右侧必须命中护栏理由的**专属措辞**才拆，正文为空的行**不自动处理**（交给人）。

```bash
python scripts/split_guard_reason.py                      # 只看
python scripts/split_guard_reason.py --apply              # 真写（自动备份）
```

实测（副本库）：可拆 55 / 正文为空 1（`1563`）；业务文案里自带 `｜` 的行**未被拆**。

### CR-5 · 没有日期锚点却在比时刻，还把"缺锚点"说成"格式错"

**现象**：10 页语料 `production_date` **10/10 页全空** ⇒ `_parse_time("12:00","")`
返回 `None` ⇒ R1-a/R1-b 的时序比较**一条都进不去**（不是"少报"，是"静默全灭"）；
同时把格式完全正常的 `12:00`/`14:00` 报成「时间格式无法解析」（`#1602`–`#1605`）。
复核员按这条去查 OCR，而那里什么都没有问题。

**改法**：`parsing.page_anchor_date(page)` —— `production_date` 优先，缺失时回落到
该页**签名日期众数**（平票取先出现者）。`rule_time._clock_needs_anchor` 把两种失败
分开：字面量里**确实有可读时刻**却解析不出 ⇒ 文案写「未找到可用于定位日期的生产
日期/签名日期，无法核对时间顺序」；字面量真的坏了才写「格式无法解析」。

### CR-6 · 跨零点被当成倒序

**现象**：`#1482`（p24 `14时12分 → 08时18分`）、`#1511`（p11 `23:04 → 00:04`）、
`#1510`（p33 `20:21 → 00:17`）全是跨日生产的正常写法；`#1426` 是 LLM 对同一现象
的复述。

**改法**：`parsing.crosses_midnight` —— 两侧都无日期、时刻往回、**隐含时长 ≤ 20h**
才按跨零点处理（20h 是实测标定：p24 的 18.1h 要放过，同日矩阵 `09:10→08:50`
隐含 23.7h 必须仍报）。**刻意收窄**：只在**同一工序内部**（起止 / 测量行序列）生效，
跨工序边界不生效（否则 B1-9 的"真倒序"检测强度被静默削弱）。LLM 侧新增
`llm_finding_guard._is_cross_midnight_clock_claim`（两个裸时刻 + 无日期/日号 +
无两个不同页码 + 有先后关系词 ⇒ 不可证伪 ⇒ 抑制并记账）。

### CR-26 · `step_no` 递增 ≠ 时刻必须递增

**现象**：`#1483`（p10 工序3「25%氯化钠溶液**配制**」10:15 vs p9 工序2 的 11:04）——
溶液是提前配好的，工序号只表示记录编排顺序。

**改法**：跨页比较里，本步属"准备类工序"（配制/配置/清洗/清洁/领用）时不报；
**年份差 >2 的提取错误仍照报**（豁免不覆盖它）。

> `N日H时M分` 解析（如 `21日07时49分`）经复核**本来就能解析**（B1-16 的
> `_CN_DAY_TIME_RE`，允许空格、窗口 ±1 天）。剩余 8 条"无法核对"全部落在
> **无锚点页**（51 页的 p8/p19/p40/p45/p48），是 CR-5 的"如实说没核对"分支，
> 不是解析缺陷。

## R102b · CR-14 **暂缓**（2026-10-23，附两次实测反例）

CR-14 的改法原文：「按"事实指纹"（页 + 类型族 + 关键实体集合）跨 source 去重，
保留最高证据等级的一条，其余降为"另有 N 处同源提示"」；验收「10 页 47 → ≤25；
p4 五重 → 1；p6 五重 → 1」。

**我按这个判据做了两版离线试算，两版都在真实语料上丢了信息。结论：这条判据在
当前抽取粒度下不可实现 —— 不是难，是"按它实现必然静默漏识别"。**

### 试算一：按"定位实体集包含"合并（角色 ∪ 工序号）

规则：同页同类型族，且 `keep 的角色集 ⊇ drop 的角色集`、`keep 的工序集 ⊇ drop 的`。

| 结果 | 反例 |
|---|---|
| 47 → 43 | **#1632「工序10 缺少 QA 签名」吞掉 #1603「工序10 时间格式无法解析」** —— 两者只是"同一页同一工序"，缺陷种类完全不同 |

根因：`completeness` 占全部条目的 86.5%，它下面混着"缺某栏签名 / 时间格式无法解析 /
参数矩阵缺列 / 勾选与选项不一致"四种**互不相干**的缺陷。**类型族太粗，不能当"同一事实"的判据。**

### 试算二：加文本相似度闸门（字符 bigram Jaccard ≥ 0.55）

规则：同页同类型族 + 文本足够像 ⇒ 合并，保留证据等级高的。

| 结果 | 反例（全部 sim ≥ 0.6） |
|---|---|
| 10 页 47 → 43 | **#1611（工序8 自我复核）吞掉 #1612（工序9）、#1613（工序10）** —— 三条文案只差工序号，而工序号是数字，被归一化掉了 ⇒ sim = **1.0** |
| 51 页 206 → 186 | **#1633「缺少 QA 签名」吞掉 #1635「缺少复核人签名」**（sim 0.63）—— 不同栏 |
| | **#1507「是否发生变更」吞掉 #1508「是否发生 OOS/OOT」、#1509**（sim 0.81/0.88）—— 不同检查项 |
| | **#1487（工序4 时间格式）吞掉 #1488（工序5 时间格式）**（sim 0.59）—— 不同工序 |

根因：**让两条 finding"长得像"的正是模板句式，让它们"不是一回事"的恰恰是工序号/
栏名/检查项名** —— 而后者在文本里只占几个字符，相似度看不见它。

### 为什么这会和 CR-16 直接对撞

CR-14 要「p6 五重 → 1」，但 p6 那 5 条 `completeness` 是**三栏**：

| id | 文案 | 哪一栏 |
|---|---|---|
| #1629 | 已记录操作时间但缺少**操作人**签名 | 操作人 |
| #1633 | 缺少 **QA** 签名 | QA |
| #1635 | 缺少**复核人**签名 | 复核人 |
| #1592 / #1618 | 执行人、检查人签名缺失（LLM 的**汇总**说法） | 三栏 |

并成 1 条就答不出"到底哪一栏没签"—— 而 CR-16 明写「空槽必须**独立成条**并指明是哪一栏」。
**两条 CR 在同一个页型上互相矛盾**，与 R102a 里 CR-29 vs CR-28 那处同源：
验收数字是按"条数"定的，缺陷却是按"栏/工序"定义的。

### 结论：真正的阻塞点是**抽取粒度**，不是去重算法

所有"合并 / 判空槽 / 判页型 / 判版本号栏"的活（CR-14、CR-16、CR-3、CR-9、CR-31）
都卡在同一件事：**`structured_json` 里的 finding 只有自由文本 `description`，
没有机器可读的「缺陷定位」**（页 + 工序 + 栏/槽 id）。没有它，任何"同一事实"的判据
都只能靠文本猜，而上面四个反例证明文本猜不准。

⇒ 建议的前置项（**需用户决定，因为动 prompt 契约**）：抽取阶段为每条 finding 输出
`defect_target = {page, step_no, slot_id}`，`slot_id` 取自该页型的栏位表。
有了它，CR-14 的"事实指纹"就是 `(page, type, slot_id)` —— **可判定，不需要猜**。

⚠️ 在拿到 `slot_id` 之前，**本批不实现 CR-14**。硬做出来的版本会在 51 页语料上
静默合并 20 条，其中至少 4 类是真缺陷（见上表）—— 这比"多 20 条噪声"糟得多。

## R104 · 已完成 P0-3 / P1-6（2026-10-26）

### P0-3 · 启动恢复与看门狗都必须持数据目录锁 —— ✅ 完成

**问题**：`recover_stuck_jobs` 的判据只有
`status IN (非终态) AND created_at < 进程启动时刻`，**没有任何 liveness 检查**。
第二个进程（冒烟实例 / dev uvicorn / 用户再开一个 exe）连同一个
`%APPDATA%\PBC\data.db` 启动，就会把第一个进程**正在跑**的 job 判成 error。
R103 只隔离了端口与 APPDATA，治的是当前那条触发路径，不是这个根。

**改法**：新增 `core/instance_lock.py`（标准库 `msvcrt.locking` / `fcntl.flock`，
无新依赖）。**只有拿到 `<db_dir>/server.lock` 独占锁的进程**才允许执行启动恢复
**和**运行时看门狗 —— 后者按 `last_activity_at` 判停滞，对"别人正在跑的 job"
同样会误判，是同一个坑的另一种触发方式。

**为什么不用 `owner_pid` + 心跳**：崩溃恢复与"另一个进程还活着"在时间上无法区分。
进程刚被杀时心跳必然"很新"，按心跳判活会**漏掉真正的崩溃** ⇒ job 永远停在非终态
（无终态黑洞，比误判更糟）。锁没有这个矛盾：持锁者一死，内核立刻释放。

**锁跟着「库」走，不跟着 APPDATA 走**：`lock_path()` 默认取
`config["app"].database_path` 的父目录。被保护的是那个库；而且测试把库指到
`tmp_path` 时锁自动隔离 —— 否则跑测试会去抢用户真实 APPDATA 里的锁，
既污染外部状态，又会在用户开着应用时让测试里的启动恢复被静默跳过。

**判据**：
- 单元 15 条（`test_r104_instance_lock.py`）：第二个持有者拿不到锁、幂等、
  释放后可再取、闸门在别人持锁时返回 False、`main.py` 三处结构不变式；

- **应用级 e2e**（`devlogs/_verify/r104_e2e_lock.py`）**3/3**：真起两个 `server.py`

## R106 · P1-3 之一：整栏全空 = 抽取不可判（2026-10-26）

### 做了什么

新增 `core/blank_column.py`，接在守卫链写路径（`apply_review`）上：
把"某列整列都空"的断言从 `completeness`（记录缺失）改判为 `ocr_noise`（识别问题），
文案换成不可判 —— 「第N页「确认」栏整列未识别到任何内容（13 行全空），
无法判断是未填写还是 OCR 未识别，请核对原页」，原文进 `guard_reason`。

### 为什么在守卫链而不是规则层

规则层拿到的是**结构化数据** —— "这一列在原文里整列空"这个信息在结构化时就丢了。
只有守卫链同时握着 `raw_by_page`。这不是偏好问题，是信息可得性问题。

### 表头识别为什么要处理 rowspan

实测那张表的**第一列**就带 `rowspan="2"` / `rowspan="4"`，后续行因此少一个 `<td>`。
按"列数相等"筛选会把整张表筛掉 ⇒ 检测器**静默失效**（看起来"没有整列空"）。
必须先展开成规整网格再谈"第 i 列"。变异 M16 专门打这个点。

### 保守性（宁可漏判，不可错改）

四条同时满足才算"整列空"：
1. 找到像表头的行（都非空、≤10 字、不含纯数字/日期）；
2. 其后 ≥2 行同宽数据行（一行空可能只是没填）；
3. 表格本身有内容（≥一半的列在多数行里有值，否则是"空表"不是"某列空"）；
4. 该列所有数据行都为空。

文案侧还要**同一句**里同时出现系统性措辞（所有/均/整栏…）、空措辞（空白/未勾选…）
与列名 —— 跨句匹配会把单格问题误改成不可判（实测文案常把两者写在一段里）。

## R105 · 已完成 P1-4（2026-10-26）

### P1-4 · 前提不可判：LLM 的"同一人"断言不得建立在不可靠读数上 —— ✅ 完成

**一句话**：规则层说"这两个名字读不准，请核对原页"，LLM 不能拿同一次读数
去断言"就是同一人"。

**改法**：`stage3` 的跨源去重处新增一条判据（两个模块级函数，
`_unreadable_signature_pages` / `_is_unfounded_self_review`）：
规则层对某页发过 `signature_unreadable` ⇒ 该页的 LLM `self_review`
（`llm_cross` / `llm_fallback`）抑制，明细进审计 `covered_by=rule_unreadable`。

**为什么是页级而不是工序级**：CR-4 的 `signature_unreadable` 只在
**该页所有工序对都至少一侧低置信**时才发 —— 它本身就是"整页没有一对可靠签名"
的结论。规则层若真有一对可靠签名，它会直接发 `self_review`，那时
`rule_covered` 的精确类型去重已经拦住 LLM 的重复，轮不到这条判据。

**判据**：
- 单元 **19 条**（`test_r104_self_review_premise.py`）：集合口径（只认 rule 来源）、
  类型归一、谓词矩阵（类型/来源/页码三个维度各配反向控制）、p4 真实一对还原；
- 管道级 **2 条**（`test_pipeline.py::TestStage3CoverageGaps`）：
  真跑 `_run_stage3_cross_analysis`，断言只剩规则层那条 info；
  反向控制：规则层没发 `signature_unreadable` 时 LLM 那条照常入库；
- 变异 **M10–M13 全 CAUGHT**：M10 = 集合恒空（判据写了但不触发，最像"已修好"），
  M11 = 不限类型（同页真缺陷被连带抑制），M12 = 不限来源（LLM 自己说"读不清"
  就能放行同页缺陷），M13 = 把 `user_rule` 也当可抑制（用户显式规则被吞）；
- **真实语料回放**：6 个 job / **791 条** → 抑制 **1 条**（就是 p4 那条），
  无连带误伤。
- ⚠️ **全量门禁抓到 1 条真红**：`test_type_sync.py` 的 AST 护栏 —— 它把
  "对 `findings` 做归一"当成"改写了集合"，要求该集合先富集。修法不是改护栏，
  而是**根本不需要归一**（`signature_unreadable` 是规则层写死的规范字面量），
  改成大小写无关比较。**教训：改 `stage3.py` 必须跑 `test_type_sync.py`** ——
  它不 import 被改模块，只读源码 AST，按模块圈影响面会漏掉它。

⚠️ **已知边界（不得读成已覆盖）**：`llm_page` 版不在范围内 —— 页级 findings
在 Stage 2 就落库，那时规则层还没跑；要覆盖得回头改已落库的行，而 `findings`

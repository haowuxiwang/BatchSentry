## 2. F1 · `retry` 全量删 findings

### F1-1 定位：先把「重跑语义」定下来（**行为决策，需你拍板**）

当前两处实现给了两个答案：

| 位点 | 删什么 | 保留什么 |
|---|---|---|
| `stage3.py:166-170` | LLM 生成 **且** 仍待审 | 全部 rule 行 + 已裁决行 |
| `actions.py:92`（retry） | **全部** | 无 |

**三个候选语义**（必须选一个，否则修了也是拍脑袋）：

- **(A) 保留已裁决**（推荐）：只删 `pending`，已裁决行留在原表并标记
  `superseded_by_run`；报告默认只统计当前 run。
  → 优点：人工工作不丢；缺点：表会累积，需要 run 维度。
- **(B) 全量归档后重来**：删全部，但**先写归档表**，报告可追溯历史。
  → 优点：语义最干净（重新分析 = 新 run）；缺点：多一张表 + 查询要带 run。
- **(C) 拒绝重跑已裁决的任务**：有 `confirmed/rejected/corrected` 时 409，
  要求先「归档任务」再重跑。
  → 优点：最保守、最符合 GMP；缺点：用户多一步。

> **我的建议：(B)**。它同时满足「重新分析语义干净」与「审计不遮蔽先前记录」
> （21 CFR 11.10(e)），且不需要给 findings 加 run 列（用 `archived_at` + `job_id`
> 即可）。**但在你确认前，F1-3 之后的步骤不启动。**

- [x] **F1-1** 选定 (A)/(B)/(C)，写进本文件与 `docs/TODO.md` 该条
  —— **选 (B)**：全量归档后重来。理由：A 会改变用户可见行为（已裁决行留在复核页，
  而按钮承诺的是「完整重新分析」）；C 多一步操作且要新造 409 分支；B 是**唯一
  既不改 UX、又消灭数据丢失**的选项。

**四条偏离（都必须读）**

1. **F1-2.2「先红后绿」没做。** 我是先写实现、再写用例，然后用**变异**证明用例有判别力
   （M1 关掉归档 ⇒ 归档用例红；M3 只归档不删 ⇒ live 用例红）。
   效果等价于「用例不是空断言」，但**不等于**「先证明它能红」—— 后者还能额外证明
   「这条用例在缺陷存在时确实会失败」，而我的做法只证明了「改动会让它失败」。
2. **没建 `core/pipeline/findings_reset.py`（F1-4.1 未做）。** 原计划让 `stage3` 与 `retry`
   共用唯一入口。但两者语义**本来就不同**（stage3 只删「LLM 生成且待审」），
   合并等于把 stage3 的口径也一起改了 —— 那是**第二个行为决策**，不该顺手做。
   现状：两处仍是两份实现，但**各自都有注释指向对方**；这是**已知分叉**，不是遗漏。
3. **`_migrate_v14` 里没有 DDL（自撤销初稿）。** 初稿在迁移体里复制了一份
   `CREATE TABLE IF NOT EXISTS`，理由是"老库要补表"。**这个理由是错的**：
   `get_db()` 是 `migrate()` 的唯一调用方，且它**先**跑 `init_schema()`
   （`schema.sql` 全量执行）⇒ 走到 v14 时表**一定已存在**，那份 DDL 只会被
   `IF NOT EXISTS` 静默跳过 —— **死代码**。它还顺带把"建表"伪装成迁移的职责，
   并给两份 DDL 留了静默漂移的空间（`_migrate_v11` 的 docstring 明令禁止）。
   现改为：DDL 只在 `schema.sql`，迁移体只留一条日志 + 一条机检。
   ⇒ 连带**作废**了初稿写过的"故意不套 try/except"（没有 DDL 就没有异常要 catch）。
4. **列名与原计划不同**：`id`→`archive_id`（避免与 `finding_id` 混淆）、
   `orig_finding_id`→`finding_id`；索引 `(job_id)` 而非 `(job_id, archived_at)`。

### 1.2 OCR 配置真值源（单一真值）

`core/pipeline/ocr_support.py`：

- `remote_backend_configured(name)`：paddle = `bool(api_url and token)`；mineru = `bool(token)`。
- `is_backend_available("docling")`：探测可选依赖。
- **`ocr_chain_configured()`**（L214）= 任一远程后端凭据完整 **或** docling 可用。
  **已是上传页横幅（`main.py:597`）的唯一来源**。

⇒ **上传门必须复用 `ocr_chain_configured()`**，否则"横幅说 OK / 上传却拒绝"会漂移。

### 1.3 影响面（blast radius）—— 实测

**单测/集成**：`tests/conftest.py::test_db`（L134）**已注入 mock LLM key** 以绕过 LLM 门。
**全部** `client` fixture（约 20 个测试模块）都由 `test_db` 派生
⇒ **只需在 `test_db` 里同样注入 OCR 凭据**，即可一次性满足新门。
未注入的话，所有"期望 200"的上传用例会**全红**。

**产物级**：
- `tests/e2e_rejections.py`（34 例）：**必须 seed OCR**，否则 19 条"期望 200"变 400。
- `tests/e2e_frozen.py`：**已有** OCR 注入逻辑（L344-375，经 `/api/settings` POST），
  并按"应用自报"算 `OCR_CONFIGURED`（L387）。**但其 upload 步骤（L431-440）无条件
  断言 200** ⇒ 若本轮未注入且 appdata 无凭据，会 fail。**须改为条件化**。

### 1.4 共用就绪判定 `tests/e2e_proc.ocr_ready_from_settings`

纯函数，读 `ocr.paddle.configured` / `ocr.mineru.configured`（**严格**，滤占位值）。
⚠️ **它对 paddle 不检查 `api_url`** ⇒ 与门的宽松判据**不同构**：
"token 真但 api_url 空"时它说就绪、门却拒绝 ⇒ **危险方向**（驱动放行、19 例变红）。
⇒ 方案：**给它加上 paddle 的 `api_url` 前置**（tests-only 文件，不入包），使其成为
门的**充分条件**（严格 ⟹ 宽松），消除危险方向。

## 2. 代码调研结论（0-38）

### 2.1 重试链与耗时算术（已核）

- `core/page_analyzer.py`：`_PAGE_MAX_TOKENS=8000`、`_PAGE_TIMEOUT=480.0`、`_PAGE_RETRIES=2`。
- 每页**两个** `chat_json` 调用点：初始（L591，stage=`page_analysis`）+ schema 修复重试
  （L707，stage=`page_analysis_schema_fix`）。
- `llm/client.py::chat_json`（L390）：`chat()` 后若 `_parse_error` ⇒ **fix-hint 循环**
  （L439-476，最多 2 次，`retries=1`）。
- ⇒ 单页最坏成功调用数 = (1+2) × 2 = **6 次** × 480s ≈ **2880s**（+ SDK 内部退避）。
  实测（`devlogs`）：page2 首次 `373.7s`（截断）→ fix-hint `903.2s`（**仍截断**）。

### 2.2 关键缺口：`finish_reason` 全库零采集

`grep -rn finish_reason llm/ core/` ⇒ **0 命中**。
`llm/adapters/base.py::ChatResult`（L16）只有 content/tokens/model。
`llm/adapters/openai_adapter.py:88` 取 `resp.choices[0].message.content`；
`anthropic_adapter.py:107` 取 `resp.content[0].text`。**两处都没取结束原因**。

⇒ 产品**无法**区分"截断"与"格式错"，fix-hint 文案也只提"围栏/尾随文本/转义"，
**对截断型失败结构性无产**（重试必然再次打满 8000）。

### 2.3 为什么"跳过重试"是对的（证据 + 市面惯例）

- **本项目实测**：两次 `completion` 均 = 8000（= max_tokens）⇒ 同 prompt + 同预算
  ⇒ 重试**不可能**变短。fix-hint 的 903s 是**纯浪费**。
- **市面惯例**（调研见 §3）：`length`/`max_tokens` **不得当作成功**，且**不得盲目重试**；
  高风险领域（医药/合规）**必须 fail-closed**，禁止自动续写。

## 3. 市面成熟方案（GitHub / 工程博客调研，clash 7897）

### 3.1 截断型 LLM 输出（`finish_reason == "length"`）

来源：*LLM Output Length Governance in Production*（oh-bug.com，2026-07）

| 规则 | 内容 |
|---|---|
| R1 | `length`/`MAX_TOKENS` **绝不当成功** ⇒ 归入 `truncated_candidate` / `partial` |
| R2 | **不要盲目重试**；四选一：auto_continue / ask_user / **fail_with_partial** / async_repair |
| R3 | **高风险/有副作用任务禁用自动续写** ⇒ 人工确认、重规划或异步生成 |
| R4 | 提高 `max_tokens` 是**事前**预防，**不是**事后补救 |
| R5 | 必须**归一化**结束原因（统一枚举 + 保留原始值），并**记入 ledger** |
| R6 | 反模式：「只记录最终文本、不记录 stop reason」⇒ 事后无法诊断 |

**对 0-38 的映射**：BatchSentry = **GMP 合规**（R3 的高风险域）⇒ 选 **fail_with_partial**
（= fail-closed），**不** auto_continue。这正是"跳过 fix-hint 重试 + 该页转人工复核"。

### 3.2 配置前置门（preflight）

来源：kubeadm / OpenShift preflight；*启动自检：环境不对就绝不假启动*（2026-08）

- **原则**：**"环境不对，就绝不假启动"** —— 把配置错误挡在**最早**阶段，给明确报错。
- **失败处理**：配置类错误**拒绝继续**（fail-closed），**不是**降级放行。
- **占位符检测**是标准首检项（`.env` 里还是示例值 ⇒ 拒绝）。

**对 0-33 的映射**：上传门 = 入口 preflight；`ocr_chain_configured()` = 就绪判定；
文案须"明确 + 可行动"（与 LLM 门同构）。⚠️ 占位符检测：门用的是**宽松**判据
（`bool(token)`），比设置页的严格判据宽 —— 见 §1.2 的单一真值取舍。

## 4. 后端模块设计评估（用户提问："各个后端模块设计是否良好？"）

**结论：总体良好，两处可改进。**

### 4.1 良好之处

| 模块 | 评价 |
|---|---|
| `core/pipeline/ocr_support.py` | **静态能力表（`_CAPABILITIES`）为单一来源**，`describe_backend` / `is_backend_available` / `remote_backend_configured` / `ocr_chain_configured` 分层清晰；`OcrBackendUnavailable` 把"可选依赖缺失"与"运行时失败"分开 ⇒ 优雅降级。**优秀**。 |
| `_get_ocr_chain()` | 主备链 ≤2，按"第一个凭据完整且非主后端"选备选 ⇒ 天然支持第三后端。**良好**。 |
| `llm/adapters/` | `base.ChatResult` + 协议无关 `ImagePart`；adapter 只翻译协议，**重试/解析归 client**（职责单一）。**良好**。 |
| `llm/client.py` | 重试/退避/超时/审计集中一处；超时**不**叠加客户端重试（避免 12 分钟卡死）。**良好**。 |
| `core/pipeline/` | `stage1/2/3` 分离 + `dual_compare` + `self_heal` + `locks`，分层明确。**良好**。 |

### 4.2 可改进之处

1. **`ChatResult` 丢弃了结束原因**（0-38 的根因）。协议差异未归一化
   （openai `finish_reason="length"` vs anthropic `stop_reason="max_tokens"`）。
   ⇒ 应在 adapter 层归一为统一枚举（市面 R5）。
2. **OCR 后端的"可用性"是静态的**：`is_backend_available` 对 paddle/mineru 恒 `True`
   （注释说明是"保持既有 failover 语义"）。**无健康探测** ⇒ 配置正确但上游挂掉时，
   用户仍会白传。**但**：`ocr_chain_configured` 的 docstring 已明确"**不发起网络探测** ——
   连通性由设置页「测试连接」负责"。⇒ **这是有意的设计取舍**，不是缺陷；
   若要进一步改善，应新增"上游健康预检"（独立议题，**不在 0-33 范围**）。
3. **新发现（0-43，P3，见 §7）**：`core/ocr_client.py`（19 处）+ `core/page_analyzer.py`
   （4 处）含 **U+FFFD 替换字符** —— docstring/注释的编码往返损坏（**非**用户可见字符串，
   不影响功能）。已实测确认。

## 6. 0-38 实施方案（含**行为决策**）

### 6.1 决策点

**`finish_reason == "length"`（截断）时，是否跳过 fix-hint 重试？**

### 6.2 推荐：**跳过 + fail-closed**（选项 A）

| 依据 | 说明 |
|---|---|
| 本项目实测 | 两次均打满 8000 ⇒ 重试**结构性无产**；903s 纯浪费 |
| 市面 R2/R3 | 高风险域**禁止**盲目重试/自动续写 ⇒ fail_with_partial |
| 项目哲学 | GMP"宁缺勿滥" + fail-closed（该页转 `failed_pages` → 人工复核） |
| 收益 | 单页最坏 **2880s → 960s**（省 2 次 fix-hint × 480s）；不再烧 2×8000 token |

**不推荐**选项 B（截断时改"精简输出"提示 + 提高 max_tokens）：
- "精简"提示会让模型**省略结构化字段** ⇒ GMP 下**比截断更危险**（静默丢字段）；
- 提高 max_tokens 属**事前**预防（R4），且模型/网关上限未知。

### 6.3 实现面（选项 A）

1. **`llm/adapters/base.py::ChatResult`** 增 `finish_reason: str = ""`（归一化值）
   + 保留 `raw_finish_reason: str = ""`（R5：统一枚举 + 原始值）。
2. **adapter 归一化**（协议差异收敛在 adapter 层）：
   - openai：`resp.choices[0].finish_reason`（`"length"` → `"length"`）；
   - anthropic：`resp.stop_reason`（`"max_tokens"` → `"length"`；`"end_turn"` → `"stop"`）。
3. **`llm/client.py`**：把 `chat()` 的重试循环抽成 `_chat_result(...) -> ChatResult`
   （**单一真值**：一个循环、两个消费者），`chat()` 保持返回 `str`（**向后兼容**，
   既有调用点零改动），`chat_json()` 改用 `_chat_result()` 以便读到 `finish_reason`。
4. **`chat_json()`**：若 `finish_reason == "length"` ⇒ **跳过** fix-hint 循环，
   记一条区分度明确的 warning（含 `raw_finish_reason`），直接返回 `_parse_error`。
5. **（可选，GMP 追溯）** `llm_call_audit` 增 `finish_reason` 列（迁移 v-N，照
   `_migrate_v9` 范式）；`_record_llm_call` 写入。⇒ 事后可查"这页为何失败"（R6）。

### 6.4 必须的复验（改入包源）

- 重建产物（PyInstaller + electron-builder）；
- **重跑 34 例拒绝矩阵**（`tests/e2e_rejections.py`）；
- 冻结冒烟 `tests/e2e_frozen.py`（含 0-38 的截断页 `e2e_test.pdf` p2 应**更快**失败）；
- 门禁 11/11。

## 1. 需求背景与来源

### 1.1 需求提出方

业务部门QA（质量保证部门）。

### 1.2 现状与痛点

GMP环境下，每批产品生产完成后，纸质批生产记录（Batch Manufacturing Record）需要经过QA人工逐页审核，确认记录完整、时间逻辑合理、参数合规后，才能支持后续的批放行决策。

**现状规模：**

- 单份批生产记录约 **50页**
- 月均产生 **50–100份** 批记录
- 折算下来，QA每月需要人工审核约 **2,500–5,000页** 纸质记录扫描件

**人工审核面临的问题：**

- 工作量大、耗时长，审核压力长期存在
- 长时间逐页核对时间顺序、字段填写、参数数值，容易因疲劳产生漏检
- 这类问题（记录不完整、时间逻辑矛盾、参数超范围）本身是数据完整性（Data Integrity）内审/外部检查中的高风险点——一旦漏检，性质不是"效率问题"而是"合规问题"

### 1.3 触发因素

非单一事件触发（如某次稽查发现问题导致），而是QA审核负荷长期偏高，业务部门主动提出提效与降险需求。

### 1.4 项目目标（一句话）

构建一个基于OCR/VLM的扫描件批生产记录识别与提取工具，辅助QA完成**时间逻辑核对、数据完整性核对、参数范围核对**，降低人工审核工作量、提高问题识别一致性，同时不改变现有审核责任主体和签署流程。

## 2. 需求分析

### 2.1 目标（Goals）

- **G1**：显著降低QA审核单份批记录所需的人工时间
- **G2**：提高时间逻辑矛盾、字段缺项、参数超范围三类问题的识别覆盖率和一致性，减少人为疲劳导致的漏检
- **G3**：审核过程可留痕、可追溯——工具的判断依据、版本、运行记录均可回溯查证

### 2.2 非目标（Non-goals，一期明确不做）

- 不做自动批放行判断——工具输出仅供QA审核参考，不构成放行依据（"纯辅助"定位）
- 不替代纸质原始记录作为 source of truth——提取/校验结果不作为主记录
- 不涉及批记录电子化/无纸化转型（EBR）——**假设**车间仍按现有方式在纸质记录上手工填写，本工具只处理"已完成填写、经扫描"的PDF文件。⚠️ 这条假设比较关键：如果理解有误，第3、4节的流程图都需要重新画，建议优先确认
- 一期不覆盖批记录之外的其他文件类型（批包装记录、检验记录等），如有需要可作为后续迭代方向

### 2.3 目标用户角色（初稿，待确认细化）

| 角色              | 说明                                 | 是否为本工具直接用户                       |
| ----------------- | ------------------------------------ | ------------------------------------------ |
| QA审核员          | 日常执行批记录审核的一线人员         | 是，主要用户                               |
| QA负责人/审核主管 | 可能需要审核进度、异常统计的汇总视图 | 待确认是否需要                             |
| 车间/生产部门     | 记录的产生方                         | 否（除非涉及问题记录退回补充流程，需确认） |

### 2.4 核心需求拆解

1. 扫描件PDF识别与提取——印刷体（模板固定内容）与手写体（人工填写内容）分开考虑，两者识别难度和准确率目标不同
2. 时间逻辑校验——跨步骤时间顺序是否矛盾、是否超出工艺规定时限
3. 数据完整性校验——必填字段是否存在遗漏
4. 参数范围校验——数值型参数（称量、温度等）是否落在规定范围内
5. 异常标记与人工复核路由——AI定位疑点，人工确认，人工始终是最终判断者
6. 结果留痕/审计追踪——每次运行的输入、模型/规则版本、输出判断均可追溯。虽是"纯辅助"工具，但只要输出用于支持GMP相关审核决策，建议仍按计算机化系统对留痕的一般要求预留能力，为后续内审/飞检做准备

### 2.5 关键假设与待确认依赖 ⚠️

以下这条是决定"参数范围校验"功能能否落地、以及工作量大小的关键前提：

**参数合规范围的"标准答案"目前从哪里来？——已确认（情况 2）：**

> 参数范围目前**只存在于纸质 / PDF 格式的工艺规程文件中，尚未结构化**，需要额外做一次提取与结构化，才能作为参数范围校验的完整标准源。

由此产生两点直接影响，已贯彻到本 PRD：

1. **项目范围必须包含"建立参数标准数据源"这一块**——即从工艺规程 PDF 提取并结构化"参数 ↔ 合规范围"，作为一项独立工作单独排期（列入 §8.2 路线图）。
2. **一期（MVP）参数校验做降级处理**：完整标准库就绪前，一期仅利用**批记录自身已印刷的范围**做规则核对，覆盖面有限，属已知且可接受的降级（见 §5.2、§2.6）。

### 2.6 产品定位原则（已确认）

本工具为**半自动辅助**系统，以下原则作为后续所有功能取舍的准绳：

- **人工始终为最终判断者**：工具输出仅供审核参考，不自动放行、不自动修正原始记录（与 2.2 纯辅助定位一致）。
- **误报优先于覆盖率（false-positive > false-negative）**：半自动下，漏报可由人工兜底，但误报会浪费 QA 时间、加重而非减轻负担——因此宁可漏检、不可乱报；校验规则须以"低误报"为第一目标。
- **允许降级交付**：当某能力（如复杂页 LLM 抽取）不稳定时，先做最小修复让其可用，不求一次完美；以"能用、可控"为先。
- **规则层优先、LLM 兜底**：确定性规则零 token 成本、低误报，应覆盖可规则化的校验；LLM 仅用于规则难覆盖的语义项。

## 3. 业务流程

### 3.1 现状业务流程（As-Is）—— 草稿，待核实修正

```
车间填写批生产记录（纸质，各工序节点操作人签字确认）
        ↓
车间/工段自检复核（是否存在此环节？待确认）
        ↓
批记录扫描 → 移交QA
        ↓
QA人工逐页审核：
  - 核对时间逻辑
  - 核对字段完整性
  - 核对参数范围
  - 核对签字/资质
        ↓
发现问题 → 退回车间补充/说明 → 重新提交审核
        ↓
审核通过 → 支持批放行决策
```

⚠️ 以上是基于通用GMP惯例画的初稿，不了解贵司实际SOP，容易画错，尤其这几处需要您核实：

- 是否存在车间/工段自检复核环节
- 审核发现问题后，退回补充的具体机制是怎样的
- 审核通过后，如何流转到放行决策环节

### 3.2 目标业务流程（To-Be）

本工具定位为 QA 人工审核的**前置辅助环节**：在"批记录扫描"之后、"QA 人工审核"之前（或与之并行）插入，先由工具完成 OCR 识别与疑点初筛，再把"带定位的疑点清单"交给 QA 做最终裁定。工具输出**仅供审核参考，不构成放行依据**（与 2.2 纯辅助定位一致）。

**一期（MVP）目标流程——本地桌面 exe 形态：**

```
批记录扫描 → 移交QA（或QA直接取得扫描PDF）
        ↓
【本工具 · 本地exe】QA在本地打开工具并上传PDF：
  1. OCR识别：印刷体（模板固定内容）与手写体（人工实测值）分开提取
  2. 时间逻辑校验：主规则=按页码时间单调不减；辅助=工序内 start≤end、异常日期、签名时间
  3. 数据完整性校验：必填字段缺项识别
  4. 参数范围校验：文档自带工艺范围→规则核对；无范围/复杂项→LLM兜底
  5. 输出"带定位的疑点清单"（页码 + 原文片段 + 疑因说明）
        ↓
【QA人工复核 · 工具内置浏览器复核页】
  - 左：原PDF（按页码定位）  右：OCR文本 + 疑点卡片
  - 逐条「确认 / 驳回 / 修正」，人工始终为最终判断者
  - 可导出审核报告（Markdown / JSON）
        ↓
审核通过 → 支持批放行决策
```

> 注：云端/私有化部署、飞书多维表格复核层为**后续路线图**（见 6.1、8.2），不在一期 MVP 范围。

## 4. 用户流程

以主要用户「QA审核员」为例，单次审核的操作路径如下：

1. **打开工具**：双击本地 exe，浏览器自动打开上传页（`GET /`）。
2. **上传PDF**：拖拽或选择批生产记录扫描件 → 工具校验为 PDF → 生成 job_id 并落库 → 后台启动分析流水线（OCR → 每页 LLM 抽取 → 跨页分析）。
3. **等待处理**：前端显示任务进度（OCR 完成页数 / 分析进度 / 疑点计数）。
4. **进入复核页**：处理完成后进入 split-pane 复核页（`GET /jobs/{id}/review`）：左侧原 PDF（按页码定位），右侧该页 OCR 文本 + 疑点卡片。
5. **逐条裁定**：对每条疑点选择：
   - **确认（confirmed）**：认可为真实问题；
   - **驳回（rejected）**：判定为误报；
   - **修正（corrected）**：人工填写正确值 `corrected_text`。
     每次裁定记录操作人备注 `reviewer_note` 与时间戳，可追溯。
6. **导出报告**：全部疑点处理完毕后，导出 `report.md` / `report.json`，随批记录归档。

> 工具不自动放行、不自动修正原始记录；所有结论以 QA 人工裁定为准（与 2.2 纯辅助定位一致）。

## 5. 功能需求与页面结构

本期（MVP）按"本地 exe + 内置浏览器复核页"实现，**范围收敛为丝裂霉素单一模板**——先保证这一种模板端到端跑通且低误报，多产品多产线（多模板）与飞书多维表格复核/统计层均为**后续路线图**（见 8.2），不在一期范围。

#### 5.1 功能模块

| 编号 | 功能                 | 说明                                   | 对应实现                                                   |
| ---- | -------------------- | -------------------------------------- | ---------------------------------------------------------- |
| F1   | 文档上传与任务管理   | 上传 PDF、生成任务、查看进度           | `api/jobs.py` `POST /api/jobs`、`GET /api/jobs/{id}` |
| F2   | OCR 识别与结构化提取 | 印刷体/手写体分开；逐页输出结构化 JSON | `core/ocr_client.py`、`core/page_analyzer.py`          |
| F3   | 跨页合规分析         | 规则层（确定性）+ LLM 层（语义兜底）   | `core/cross_page_analyzer.py`                            |
| F4   | 疑点复核与人工裁定   | 确认/驳回/修正 + 留痕                  | `templates/review.html`、`api/review.py`               |
| F5   | 报告导出             | Markdown / JSON                        | `api/report.py`                                          |

#### 5.2 校验能力范围（核心，回答 2.5）

- **时间逻辑校验——主规则：按页码单调不减（已与业务确认）**

  - **核心规则**：批记录按页码顺序即为时间推进顺序。把每页抽取到的时间戳按页码排列，若某页出现比前面页更早的时间，即为疑点（时间倒流）。这是**确定性规则**，零 token 成本、天然低误报，是一期时间校验的主体。
  - **比较语义**（建议，待细化）：第 N 页的最晚时间 ≤ 第 N+1 页的最早时间；无时间的页（封面、目录、图表页）跳过，不参与比较。
  - **控误报边界（关键，半自动定位下必须处理）**：
    - ① 无时间页 / 时间抽取失败页跳过，不报；
    - ② 一页多个时间时按上面的"最晚 ≤ 下一页最早"处理，避免同页内多时间被误判；
    - ③ OCR 把时间读错会造成假倒流——低置信度时间不直接报，或降级为提示而非 critical。
  - **辅助规则**：工序内 start ≤ end（单步骤自洽）；异常日期（未来日期、格式非法）。
  - **签名时间**：签字/复核时间是否落在对应操作时间窗内——规则难覆盖时用 LLM 兜底。
  - **注**：原代码"取全文档众数年份"的检查方向错误（合法多年份会误报），一期用"按页码单调性"替代。
- **参数范围校验（规则优先 + LLM 兜底）**

  - **合规范围的真实来源（见 §2.5，已确认为情况 2）**：完整的"参数 ↔ 合规范围"标准目前**只存在于纸质 / PDF 工艺规程中、尚未结构化**；建立"工艺规程标准库"是一块需单独排期的工作（列入 §8.2 路线图），一期不建。
  - **一期折中做法**：优先利用**批记录自身已印刷的范围**（如"理论产量(1300~3200)g""实际收率≥30%"），由 F2 抽取 `spec_range` 与 `value`，规则核对 `value ∈ range`——零额外成本、低误报；
  - 记录未印范围、或结构复杂（如第 9 页"4 列 × 11 时间点 × 2 指标"流速/压力矩阵）的项，一期**不强行判定**（避免误报），转 LLM 语义提示或留待标准库就绪后覆盖；
  - **已知降级**：因完整标准源缺失，一期参数范围校验覆盖面有限，属已知且可接受的降级（与 §2.6"允许降级交付"一致）。
- **数据完整性校验**：必填字段（批号、文件编号、各工序操作人/复核人、关键参数）缺项识别。

#### 5.3 页面结构

- **P1 上传页**（`templates/upload.html`）：拖拽上传 + 历史任务列表；
- **P2 复核页**（`templates/review.html`）：左原 PDF / 右 OCR 文本 + 疑点卡片，逐页逐条裁定；
- **P3 报告**：导出为本地文件（非独立页面），`report.md` / `report.json`。

## 6. 非功能需求

### 6.1 部署

**一期（MVP）= 本地桌面 exe（已确认形态）**

- 以 PyInstaller 将 `main.py` + 依赖打包为单目录 exe；QA 双击运行，浏览器自动打开内置 UI。
- 单用户、本机运行；上传的 PDF 与提取结果**不出本机**。
- OCR / LLM 调用所需密钥仅存于本地 `.env`（已 gitignore），**严禁硬编码入源码**；如需走公网 API，验证阶段应使用历史/测试数据脱敏，避免真实生产数据出网。

**后续路线图 = 私有化 / 云端部署**

- 生产环境阶段可转为私有化或云端部署，消除公网 API 出网风险；
- 复核/统计层可对接飞书多维表格（见 5、8.2）。

**待补充**：单份 50 页文档端到端处理时长预期（受 OCR/LLM API 限速影响）、并发峰值分布（月 50–100 份如何分布）。

### 6.2 安全与合规

- **数据出内网限制**：MVP 本机运行，PDF 与记录不出本机；若 OCR/LLM 走公网 API，验证阶段须用历史/测试数据脱敏，禁止真实生产数据出网。路线图通过私有化部署消除该风险。
- **审计追踪（Audit Trail）**：每次运行须留痕——输入 PDF、模型/规则版本、输出疑点、人工裁定（confirmed/rejected/corrected + `reviewer_note` + `corrected_text` + 时间戳），均可回溯，为后续内审/飞检做准备（与 G3 一致）。
- **权限控制**：MVP 单用户，无需登录；路线图按需引入账号/角色与操作权限。
- **密钥管理**：API key 仅存 `.env`（gitignore），禁止硬编码；`.env.example` 提供字段模板。

## 7. 验收标准

**准确率目标原则（已确定）**：印刷体与手写体字段设置**不同的提取准确率目标**，不用同一笼统数字。

- **提取准确率**

  - 印刷体字段（标题 / 文件编号 / 批号 / 工序步骤 / 印刷体参数范围）：目标 ≥ 95%（建议值，待摸底校准）；
  - 手写体实测值 / 签字：目标待历史记录摸底后定，不直接拍硬指标（手写上限本就低于印刷体，见 8.1）。
- **里程碑 0（当前首要目标）**：丝裂霉素样本**端到端跑通一次**——OCR → 每页抽取 → 跨页分析 → findings 入库 → 复核页可查 → 报告可导出，无中断、无超时。这是当前尚未达成、必须先过的门槛（见 §10）。
- **功能验收（一期必须）**

  1. 时间校验：**按页码单调性主规则**已实现（规则层），并处理无时间页/多时间页/低置信度三类误报边界；工序内 start≤end、异常日期辅助规则可用；签名时间可由 LLM 兜底；
  2. 参数范围：文档自带范围项规则核对准确率达标；LLM 兜底项**误报率可控**；
  3. **误报优先原则**：半自动定位下，`false-positive（误报）率`是核心验收指标，须低于约定阈值（阈值待摸底后定）；`false-negative（漏报）`由人工兜底，**不作为硬验收指标**；
  4. 人工复核闭环：确认 / 驳回 / 修正 + 留痕 + 导出，全链路可用；
  5. 留痕完整：每次运行输入、模型/规则版本、输出、人工裁定均可追溯。
- **性能验收**：单份 50 页端到端（OCR + 分析 + 入库）时长待定（受 API 限速影响，见 6.1 待补充项）。

### 8.1 已识别风险（初稿）

| 风险                        | 说明                                                               | 应对方向（初步想法）                                                     |
| --------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| 手写体识别准确率不确定      | 关键字段（签字、实测数值）多为手写，准确率上限低于印刷体           | 建议先用一批历史真实记录做准确率摸底测试，再定验收标准                   |
| 参数标准数据源缺失/不结构化 | 已确认（情况2）：范围仅存于工艺规程 PDF，尚未结构化（见 §2.5）                                                              | 一期先用记录自带范围；完整"工艺规程标准库"需单独排期（见 §8.2）                                                           |
| 批记录模板差异              | **已确认为多产品多产线、多模板**；模板差异显著影响提取稳定性 | MVP 收敛为丝裂霉素单模板先跑通；多模板作为后续迭代，届时再评估模板配置层 |
| 端到端尚未跑通              | 当前连单份样本都未完整跑通（复杂矩阵页超 token/超时）              | 里程碑 0 优先：调大 max_tokens、拆分复杂页、必要时降级抽取粒度           |
| 单一样本、缺历史数据摸底    | 目前仅 1 份样本，无法校准准确率/误报阈值                           | 尽快取得一批历史真实记录做摸底，再定 §7 验收阈值                        |

### 8.2 迭代规划

**一期（MVP，当前范围）**：本地 exe；OCR + 每页 LLM 抽取 + 跨页规则/LLM 分析；时间校验（按页码单调性主规则 + 工序内/异常日期辅助）+ 参数范围（仅记录自带范围，规则优先 + LLM 兜底）；内置浏览器复核页 + 报告导出。

**准确率摸底**：用一批历史真实记录，测印刷体/手写体提取准确率与误报率，校准第 7 节验收阈值，再定全量上线标准。

**全量上线**：基于摸底结果调优（prompt / 规则 / 误报控制）后，正式全量推广。

**后续路线图（非一期）**：

- **工艺规程标准库**：从纸质/PDF 工艺规程提取并结构化"参数 ↔ 合规范围"（当前范围仅存于工艺规程 PDF，见 §2.5），作为参数范围校验的完整标准源——参数校验完整落地的前置依赖；
- 私有化 / 云端部署（消除公网 API 出网风险）；
- 飞书多维表格复核 / 统计层；
- 多用户、权限与并发；
- 扩展文件类型（批包装记录、检验记录等）。

> "全量覆盖"指最终目标范围（上线节奏），并非缩小一期范围。

### 数据契约（给开发，避免翻代码踩坑）

- 页面接口 `GET /api/jobs/{id}/pages/{page}` 返回 key 为 **`structured`**（非 `structured_json`）；
- findings 列表接口返回 `{findings:[...], count:N}`；
- DB `findings.type` 为 TEXT，不强制枚举——LLM 返回的新类型能入库，但与 `FindingType` 枚举不同步，按枚举过滤会漏数据（见上表"数据模型/枚举"行）。

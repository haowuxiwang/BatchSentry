## 第二步：需求分析

### 2.1 问题是什么

QA 每月需要人工逐页审核 2,500–5,000 页纸质批生产记录扫描件，面临三大问题：

1. **工作量大、耗时长**：逐页核对时间顺序、字段填写、参数数值，审核压力长期存在
2. **疲劳导致漏检**：长时间重复核对，注意力下降，漏检率不可控
3. **漏检后果严重**：记录不完整、时间逻辑矛盾、参数超范围是 GMP 数据完整性（Data Integrity）内审/飞检的高风险点——漏检不是"效率问题"而是"合规问题"

### 2.2 根因是什么

| 根因层级             | 说明                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------- |
| **直接根因**         | 批记录页数多（50 页/份），审核负荷超出单人的注意力容量                                 |
| **深层根因**         | 纸质记录 → 扫描件 → 人工逐页核对，这个流程天然没有"自动筛选疑点"的能力，全靠人眼扫全量 |
| **结构性根因**       | 审核标准（时间逻辑、字段完整、参数范围）是确定性规则，但执行方式是纯人工逐条比对——规则可确定但执行靠人力 |

根因分析结论：**问题本质是"确定性规则的执行方式低效"**，适合用规则引擎+AI辅助来提升执行效率。

### 2.3 值不值得做

| 维度         | 评估                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------- |
| 业务紧迫性   | 高——GMP 合规刚性要求，漏检后果严重                                                       |
| 受益面       | QA 全体审核员，月均 50–100 份批记录都受益                                                |
| 投入风险     | 中——OCR/LLM 技术不确定性（手写体识别、复杂表格抽取），但半自动定位允许降级交付           |
| ROI 预期     | 🔴 待补充——需 QA 提供当前审核时长数据后才能估算节省时间                                  |

**结论：值得做**，但需允许降级交付，不追求一次完美。

### 2.4 有哪些方案

| 方案 | 描述                                                                 | 优点                          | 缺点                              | 取舍判断 |
| ---- | -------------------------------------------------------------------- | ----------------------------- | --------------------------------- | -------- |
| **A：纯规则引擎** | 先数字化审核 checklist，QA 人工录入数据，规则自动判定                 | 低技术风险，确定性高          | 人工录入工作量等于当前审核量，不省时 | ❌ 不选——录入工作量不减 |
| **B：OCR+LLM+规则**（当前方案） | OCR 扫描件识别 → LLM 结构化提取 → 规则+LLM 跨页合规分析 → 人工复核 | 减少人工逐页核对工作量        | OCR/LLM 技术不确定性；复杂表格抽取风险 | ✅ 选择——半自动定位允许降级 |
| **C：EBR 电子批记录** | 产线全面数字化，消灭纸质记录                                         | 最彻底，消灭根因              | 涉及产线改造，非本项目范围        | ❌ 不选——超出范围（见 2.5） |

**选择方案 B 的理由**：
- 根因是"确定性规则的执行方式低效"，OCR+LLM 可以替代人工逐页数据提取，规则引擎替代人工逐条比对
- 半自动定位下，AI 提取有错不致命——标注低置信度让人工核，漏报由人工兜底
- 允许降级交付：先跑通核心流程，不追求一次完美

### 2.5 明确不做（Non-goals）

- ❌ 不做自动批放行判断——工具输出仅供 QA 审核**参考**，不构成放行依据
- ❌ 不替代纸质原始记录作为 source of truth
- ❌ 不涉及批记录电子化/无纸化转型（EBR）——假设车间仍按现有方式在纸质记录上手工填写，本工具只处理"已完成填写、经扫描"的 PDF 文件
- ❌ 一期不覆盖批记录之外的其他文件类型（批包装记录、检验记录等）

### 2.6 产品定位原则 🟢

以下原则作为后续所有功能取舍的准绳：

1. **人工始终为最终判断者**：工具输出仅供审核参考，不自动放行、不自动修正
2. **误报优先于覆盖率**：半自动下，漏报可由人工兜底，但误报浪费 QA 时间、加重负担——宁可漏检、不可乱报
3. **允许降级交付**：某能力不稳定时，先做最小修复让其可用，不求一次完美
4. **规则层优先、LLM 兜底**：确定性规则零 token 成本、低误报，应覆盖可规则化的校验；LLM 仅用于规则难覆盖的语义项

## 第三步：先画流程，再写 PRD

### 3.1 现状业务流程（As-Is）🟢

```
车间填写批生产记录（纸质，各工序节点操作人签字确认）
        ↓
车间/工段自检复核（已确认存在此环节）
        ↓
批记录扫描 → 移交 QA
        ↓
QA 人工逐页审核：
  - 核对时间逻辑（跨步骤时间顺序、工序内起止时间）
  - 核对字段完整性（必填字段有无遗漏）
  - 核对参数范围（称量、温度、压力等是否合规）
  - 核对签字/资质
        ↓
发现问题 → 退回车间进行笔误修正 → 重新提交审核
        ↓
审核通过 → 支持批放行决策
```

### 3.2 目标业务流程（To-Be）

本工具定位为 QA 人工审核的**前置辅助环节**：在"批记录扫描移交 QA"之后、"QA 人工审核"之前插入。

```
车间填写批记录 → 车间自检 → 扫描移交 QA
        ↓
【本工具 · OCR识别+合规分析】
  1. OCR 识别：印刷体与手写体分开提取
  2. 时间逻辑校验：规则层确定性判定
  3. 数据完整性校验：必填字段缺项识别
  4. 参数范围校验：文档自带范围→规则核对；无范围/复杂项→标注低置信度
  5. 输出"带定位的疑点清单"（页码 + 原文片段 + 疑因说明 + 置信度）
        ↓
【QA 人工复核】
  - 逐条裁定：确认 / 驳回 / 修正
  - 低置信度项重点核对
        ↓
发现问题 → 退回车间笔误修正 → 重新提交
        ↓
审核通过 → 支持批放行决策
```

### 3.3 用户流程（以 QA 审核员为例）

```
步骤1：上传 PDF
  → 拖拽或选择批记录扫描件
  → 工具校验为 PDF → 生成任务 → 后台启动分析

步骤2：等待处理
  → 前端显示进度（OCR 完成页数 / 分析进度 / 疑点计数）

步骤3：进入复核页
  → 左侧：原 PDF（按页码定位）
  → 右侧：OCR 文本 + 疑点卡片（每条标注置信度）

步骤4：逐条裁定
  → 对每条疑点选择：
     · 确认（confirmed）——认可为真实问题
     · 驳回（rejected）——判定为误报
     · 修正（corrected）——人工填写正确值
  → 每次裁定记录操作人备注 + 时间戳

步骤5：导出审核报告
  → 全部疑点处理完毕后，导出报告随批记录归档
```

### 3.4 页面结构

| 页面       | 路径                      | 内容                                  |
| ---------- | ------------------------- | ------------------------------------- |
| **P1 上传页** | `GET /`                 | 拖拽上传 + 历史任务列表               |
| **P2 复核页** | `GET /jobs/{id}/review` | 左原 PDF / 右 OCR 文本 + 疑点卡片，逐页逐条裁定 |
| **P3 报告** | 导出为本地文件           | Markdown / JSON 格式，非独立页面      |

## 第四步：补充规则细节

### 4.1 功能模块总览

| 编号 | 功能                   | 说明                                                     |
| ---- | ---------------------- | -------------------------------------------------------- |
| F1   | 文档上传与任务管理     | 上传 PDF、生成任务、查看进度                             |
| F2   | OCR 识别与结构化提取   | 印刷体/手写体分开；逐页输出结构化 JSON                  |
| F3   | 跨页合规分析           | 规则层（确定性）+ LLM 层（语义兜底）                    |
| F4   | 疑点复核与人工裁定     | 确认/驳回/修正 + 留痕                                   |
| F5   | 报告导出               | Markdown / JSON                                         |

### 4.2 F1 文档上传与任务管理

| 字段     | 说明                                                                 |
| -------- | -------------------------------------------------------------------- |
| **输入** | PDF 文件（拖拽或选择上传）                                           |
| **输出** | job_id + 任务状态（pending → ocr_running → ocr_done → analyzing → review → done | error） |
| **条件** | 文件必须为 PDF 格式；文件大小 🔴 待定上限                            |
| **状态** | pending → ocr_running → ocr_done → analyzing → review → done \| error |
| **异常** | 非 PDF 文件→拒绝上传；OCR/LLM API 不可用→任务 status=error 并记录错误信息 |

### 4.3 F2 OCR 识别与结构化提取

| 字段     | 说明                                                                 |
| -------- | -------------------------------------------------------------------- |
| **输入** | PDF 各页（OCR API 处理后返回 HTML 表格）                             |
| **输出** | 每页结构化 JSON，包含：页码、标题、文件编号、版本、批号、生产日期、工序步骤列表、时间戳、参数列表（含 spec_range 与 value）、签字信息、手写体内容、置信度标记 |
| **条件** | 印刷体与手写体分开考虑，识别难度和置信度不同                         |
| **状态** | 每页独立：未抽取 → 已抽取（含 structured_json）                     |
| **异常** | (1) 复杂矩阵页（如 4 列设备 × 11 时间点 × 2 指标）→ 可能超 token / 超时，需拆分或降级抽取粒度；(2) 封面/目录页 → steps 可能为空，不报异常；(3) OCR 把时间读错 → 标注低置信度，不直接作为规则判定依据；(4) 签名+日期粘连（如"庞明女署2027.01.17"）→ 需 regex 或 LLM 拆分 |

**印刷体 vs 手写体置信度策略** 🟢：

| 类型     | 置信度预期 | 处理策略                                                     |
| -------- | ---------- | ------------------------------------------------------------ |
| 印刷体   | 高         | 提取结果可直接作为规则判定依据；目标准确率 ≥ 95%（建议值）   |
| 手写体   | 低         | 提取结果标注 low confidence，规则不直接判定，提示人工重点核对 |

### 4.4 F3 跨页合规分析——核心规则细节

#### 4.4.1 时间逻辑校验 🟢

**主规则：按页码时间单调不减**

| 字段     | 说明                                                                 |
| -------- | -------------------------------------------------------------------- |
| **输入** | 每页抽取的时间戳列表（按页码排列）                                   |
| **输出** | finding：type=`time_reversal`，severity=critical \| warning，description 含页码+具体时间+矛盾说明 |
| **条件** | 批记录按页码顺序 = 时间推进顺序。第 N 页最晚时间 ≤ 第 N+1 页最早时间；无时间页（封面、目录、图表页）跳过不参与比较 |
| **状态** | 规则判定=确定性，无需 LLM                                           |
| **异常** | (1) 一页多个时间 → 按最晚≤下一页最早处理；(2) 无时间页 → 跳过，不报；(3) OCR 时间格式串扰（如"2022/4/202205.07"）→ regex 清洗后再比，清洗失败则标注 low confidence 不直接报；(4) 低置信度时间 → 降级为 warning 而非 critical |

**辅助规则**：

| 规则                   | 输入                   | 输出（finding type）         | 条件                     |
| ---------------------- | ---------------------- | ---------------------------- | ------------------------ |
| 工序内 start > end     | 单步骤起止时间         | `time_reversal`              | 同一工序内，开始晚于结束 |
| 异常日期               | 任何日期字段           | `suspicious_date`            | 年份 < 2000 或 > 当前年+1 |
| 签名时间早于操作时间   | 签字日期 + 操作时间窗  | `signature_time_anomaly`     | 签字日期在操作之前       |

> ⚠️ 原代码"全页众数年份"规则**方向错误**——同页可合法存在不同事件年份（如起草 2022、生产 2015、审核 2025），按众数判会误报。一期用"按页码单调性+按事件类型分组"替代。

#### 4.4.2 参数范围校验 🟢

**合规范围的来源（已确认为情况 2）**：完整"参数 ↔ 合规范围"标准目前**只存在于纸质/PDF 工艺规程中、尚未结构化**，需单独排期建立标准库（路线图 §8.2）。一期仅利用批记录自身已印刷的范围。

| 字段     | 说明                                                                 |
| -------- | -------------------------------------------------------------------- |
| **输入** | 每页参数的 spec_range + value（由 F2 抽取）                          |
| **输出** | finding：type=`param_out_of_spec`，severity=critical \| warning \| info |
| **条件** | (1) 记录自带印刷范围 → 规则核对 value ∈ spec_range，确定性判定；(2) 记录未印范围 → 不强行判定，标注 info 提示人工；(3) spec_range 格式复杂（LaTeX 残片、HTML 转义、中文表达如"不超过100次"）→ regex 解析后再判，解析失败则标注 low confidence |
| **状态** | 规则可判定 → deterministic；规则不可判定 → LLM 兜底或人工复核       |
| **异常** | (1) spec 含 LaTeX `$m^{3}/h$` 残片 → 先 strip 再解析；(2) spec 含 `<0.3MPa` → 解码 HTML 转义；(3) spec 含中文"不超过""不少于"→ regex 映射为 < / ≥；(4) 复杂矩阵（4 列 × 11 时间点 × 2 指标）→ 一期不强行逐 cell 判定，矩阵整体标注 confidence 供人工核 |

**规则解析覆盖范围**（一期）：

| spec_range 格式          | 示例             | 规则能否判定 |
| ------------------------ | ---------------- | ------------ |
| 区间（数字-数字/数字~数字） | 1300~3200, 0.5-1.0 | ✅ 规则判定  |
| 单侧（< / ≤ / ≥ / >）    | <0.3MPa, ≥30%    | ✅ 规则判定  |
| 中文（不超过/不少于/NMT/NLT） | 不超过100次      | ✅ 规则判定（regex 映射） |
| 语义描述（应澄清/应符合要求） | 应澄清           | ❌ 规则不判 → LLM 兜底或人工 |
| LaTeX 残片               | 0.5-1.0 $m^{3}/h$ | ✅ 规则判定（strip 残片后） |
| 矩阵表格                | 4列×11行×2指标   | 🟡 一期整体标注 confidence |

#### 4.4.3 数据完整性校验

| 字段     | 说明                                                                 |
| -------- | -------------------------------------------------------------------- |
| **输入** | 每页抽取的结构化字段 + 必填字段清单（模板定义）                       |
| **输出** | finding：type=`completeness`，severity=warning \| info              |
| **条件** | 必填字段为空或抽取失败 → 报缺项；模板字段清单需按丝裂霉素单模板定义 |
| **状态** | 规则判定=确定性                                                     |
| **异常** | (1) 模板字段清单未定义 → 一期先定义丝裂霉素模板的必填字段清单；(2) 某字段存在但 LLM 抽取失败 → 标注 low confidence |

**一期必填字段清单（丝裂霉素单模板）🔴**：

> 需 QA 提供该模板的必填字段列表，或从批记录模板本身提取。暂列已知必填项：
> - 批号、文件编号、版本号
> - 各工序操作人、复核人、签字日期
> - 关键参数实测值（产量、收率等）
> - 完整清单待 QA 补齐

### 4.5 F4 疑点复核与人工裁定

| 字段     | 说明                                                                 |
| -------- | -------------------------------------------------------------------- |
| **输入** | findings 列表（每条含页码、type、severity、description、ocr_text、confidence） |
| **输出** | 每条 finding 的裁定结果：status（confirmed \| rejected \| corrected）+ reviewer_note + corrected_text + reviewed_at |
| **条件** | QA 逐条裁定，人工始终为最终判断者                                   |
| **状态** | pending → confirmed \| rejected \| corrected                       |
| **异常** | (1) 低置信度 finding → 前端高亮提示 QA 重点核对；(2) 批量驳回操作 → 🔴 是否需要？待确认 |

### 4.6 F5 报告导出

| 字段     | 说明                                                                 |
| -------- | -------------------------------------------------------------------- |
| **输入** | 任务全部 findings + 裁定结果                                        |
| **输出** | Markdown / JSON 格式报告文件                                        |
| **条件** | 全部疑点已裁定后可导出；也可在中途导出（未裁定的标注 pending）       |
| **状态** | 无状态变化，一次性导出                                              |
| **异常** | 无 findings 的任务 → 报告标注"无异常检出"                           |

## 附录 A：飞书多维表格方案分析 ⚪

> 本节为参考建议，非定论。接手团队和业务方共同决策是否采用飞书方案。

### A.1 什么是飞书多维表格

飞书多维表格是飞书内置的结构化数据管理工具，类似 Airtable/Notion Database，具备：
- 多视图（表格/看板/甘特/仪表盘）
- 行级协作与评论
- 自动化流程（条件触发飞书通知/审批/ webhook）
- 飞书生态内天然多用户、多角色权限

### A.2 本项目可用飞书的环节

| 环节               | 当前方案（本地exe）                | 飞书方案                                  | 适合程度 |
| ------------------ | ------------------------------------ | ----------------------------------------- | -------- |
| **复核裁定**       | 本地浏览器复核页                    | 飞书多维表格行级操作，QA 在飞书内逐条裁定 | ⭐⭐⭐ 高——协作友好、留痕天然、负责人可看进度 |
| **统计看板**       | 无（单用户孤岛）                    | 飞书仪表盘：异常统计、审核进度、月度趋势 | ⭐⭐⭐ 高——QA 负责人视角刚需 |
| **参数标准库**     | 一期无（降级用记录自带范围）        | 飞书多维表格存储结构化"参数↔合规范围"   | ⭐⭐ 中——数据录入需人工，但表格化管理优于散落 PDF |
| **退回/补充流程**  | 无（线下退回车间）                  | 飞书审批流：发现问题→退回车间→车间补充→重新提交 | ⭐⭐ 中——需车间也用飞书 |
| **OCR+分析引擎**   | 本机运行                            | 不适合放飞书——计算密集、需调用外部 API    | ⭐ 低 |

### A.3 两种部署路线对比

| 维度           | 路线 1：纯本地 exe（当前方案）       | 路线 2：本地引擎 + 飞书复核层          | 路线 3：全飞书（含引擎）         |
| -------------- | ------------------------------------ | -------------------------------------- | -------------------------------- |
| 架构           | 本机 exe + 内置浏览器 UI             | 本机做 OCR+分析→结果推送飞书多维表格   | 飞书应用+云服务器跑引擎           |
| 数据安全       | PDF 不出本机（最安全）               | PDF 仍在本机，疑点数据推飞书           | PDF 需上传云服务器（需合规评估） |
| 复核体验       | 本地 split-pane 页面                 | 飞书多维表格行级操作+评论              | 飞书多维表格                      |
| 管理看板       | 无                                   | 飞书仪表盘                             | 飞书仪表盘                        |
| 开发门槛       | 低（Python+HTML）                    | 中（需飞书开放平台对接）               | 高（需云服务器+飞书应用开发）     |
| 多用户         | ❌ 单用户                            | ✅ 飞书天然多用户                      | ✅ 飞书天然多用户                  |
| 扩展性         | 差（单机孤岛）                       | 好（对接飞书审批、通知）               | 好                                |
| 一期可行性     | ✅ 可快速落地                        | 🟡 需额外对接开发                      | ❌ 改动量大，不适合一期           |

### A.4 建议路线 ⚪

**推荐路线 2：本地引擎 + 飞书复核层**，分两阶段：

- **一期（MVP）**：先用本地 exe 跑通核心流程（OCR → LLM → 规则 → findings），验证技术可行性
- **二期**：将 findings 结果推送到飞书多维表格，QA 在飞书内做复核裁定，负责人看仪表盘统计

理由：
1. 一期不改架构，降低技术验证风险
2. 二期对接飞书只改"复核/统计层"，不改核心引擎
3. 公司已购买飞书，多用户协作天然具备
4. 逐步推进，不一次性大改

## 附录 C：术语表

| 术语                         | 说明                                                       |
| ---------------------------- | ---------------------------------------------------------- |
| GMP                          | 药品生产质量管理规范（Good Manufacturing Practice）        |
| BMR / 批生产记录             | Batch Manufacturing Record                                |
| OCR / VLM                    | 光学字符识别 / 视觉语言模型                                |
| 印刷体 vs 手写体             | 模板固定印刷内容 vs 人工填写内容；识别难度与置信度不同     |
| findings（疑点）             | 工具检出的待人工裁定的可疑项                               |
| 规则层 vs LLM 层             | 确定性规则校验（零 token、低误报）vs 大模型语义兜底        |
| 半自动（semi-automatic）     | 工具定位疑点、人工最终裁定；不自动放行 / 不自动修正        |
| 误报率（false-positive）     | 工具报错但人工判定无问题的比例——半自动下核心指标           |
| 漏报率（false-negative）     | 真实问题未被工具检出的比例——由人工兜底，非硬指标           |
| 数据完整性（Data Integrity） | GMP 内审/飞检高风险点                                      |
| 复核状态                     | confirmed / rejected / corrected                           |
| 置信度（confidence）         | 提取结果的可靠性标记：high / medium / low                  |
